# ERP-система: бухгалтерия, документооборот, склад, финансы

Единая учётная система для бизнеса: бухгалтерия, электронный документооборот,
склад и закупки, продажи и CRM, кадры и зарплата, финансовый контроль,
аналитика и AI-помощник.

**Стек:** Django 5.2 + Django REST Framework (JWT) + PostgreSQL/SQLite,
фронтенд — SPA на чистых HTML/CSS/JavaScript без сборки и внешних зависимостей.

---

## Быстрый старт

```bash
# 1. Окружение
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # Linux / macOS
pip install -r requirements.txt

# 2. База и демо-данные (по умолчанию SQLite — Postgres не нужен)
cd app
python manage.py migrate
python manage.py seed_demo

# 3. Запуск
python manage.py runserver
```

Открыть **http://127.0.0.1:8000/**

> Если порт 8000 занят другим приложением (например, контейнером Docker),
> запустите `python manage.py runserver 8010` и откройте `http://127.0.0.1:8010/`.
> Обращайтесь именно к `127.0.0.1`: `localhost` на некоторых системах
> сначала резолвится в IPv6, где может слушать другой сервис.

### Как связаны фронтенд и бэкенд

Django рендерит `templates/index.html` и передаёт в него настройки через
`json_script` — тег `<script id="app-config" type="application/json">`.
Клиент читает его в `static/js/core/config.js` и включает режим работы
с REST API: вход по JWT, данные из базы, аудит на сервере.

Слой данных изолирован в `static/js/core/store.js`: чтение синхронное
(данные загружаются одним запросом `/api/bootstrap/` и держатся в памяти),
изменения применяются сразу и уходят на сервер, при отказе — откат.
Модули интерфейса о сети ничего не знают.

## REST API

| Метод | Эндпоинт | Назначение |
|---|---|---|
| `POST` | `/api/token/` | получение JWT (`{"login": "...", "password": "..."}`) |
| `POST` | `/api/token/refresh/` | обновление токена |
| `GET` | `/api/me/` | профиль, роль и права текущего пользователя |
| `GET` | `/api/bootstrap/` | все доступные роли коллекции одним запросом |
| `GET` | `/api/summary/` | KPI для дашборда, посчитанные на сервере |
| `GET` | `/api/reports/` | список доступных отчётов |
| `GET` | `/api/reports/<имя>/` | отчёт: `turnover`, `balance`, `pnl`, `cashflow`, `debts` |
| `POST` | `/api/assets/depreciate/` | начисление амортизации за месяц (`{"period": "2026-08"}`) |
| `GET` | `/api/assets/<id>/schedule/` | график амортизации объекта до конца срока |
| `GET` | `/api/health/` | проверка живости (healthcheck) |
| `GET/POST/PATCH/DELETE` | `/api/<коллекция>/` | CRUD по 38 коллекциям |

Коллекции: `companies`, `users`, `roles`, `settings`, `counterparties`,
`documents`, `contracts`, `signatures`, `accounts`, `entries`, `periods`,
`fixedAssets`, `depreciations`, `taxes`, `cashOrders`, `payments`,
`bankStatements`, `budgets`, `warehouses`,
`products`, `stock`, `stockMoves`, `inventories`, `purchaseRequests`,
`purchaseOrders`, `sales`, `returns`, `deals`, `tasks`, `employees`,
`payrolls`, `timesheets`, `requests`, `notifications`, `auditLog`,
`categories`, `units`.

Ключи JSON — camelCase (`counterpartyId`, `createdAt`), внутри Django — обычный
snake_case; преобразование выполняет `apps/common/serializers.py`.

Права проверяются по роли на уровне модуля: у каждой коллекции объявлен модуль
для чтения и, при необходимости, отдельный модуль для записи
(`apps/api/registry.py`). Все изменения пишутся в журнал аудита автоматически.

Отчёты принимают период: `?from=2026-01-01&to=2026-08-31` (баланс — только `to`).
Расчёт выполняется на сервере по проведённым проводкам, клиент получает готовые
строки и итоги.

Пример:

```bash
curl -X POST http://127.0.0.1:8000/api/token/ \
     -H "Content-Type: application/json" \
     -d "{\"login\":\"admin\",\"password\":\"1234\"}"

curl http://127.0.0.1:8000/api/counterparties/ \
     -H "Authorization: Bearer <access>"
```

## Основные средства и амортизация

Раздел «Бухгалтерия → Основные средства» ведёт учёт зданий, транспорта,
оборудования, техники и мебели: первоначальная стоимость, срок полезного
использования, накопленная амортизация и остаточная стоимость.

**Методы амортизации** — все четыре по МСФО (IAS) 16:

| Метод | Формула за месяц | Для чего |
|---|---|---|
| Линейный | (стоимость − ликвидационная) ÷ СПИ | здания, мебель, стеллажи |
| Уменьшаемого остатка | остаточная × коэффициент ÷ СПИ | транспорт, техника |
| По сумме чисел лет | база × (остаток лет ÷ сумму чисел лет) ÷ 12 | оборудование |
| Производственный | база × выработка за период ÷ плановую выработку | погрузчики, станки |

**Правила учёта.** Начисление идёт с месяца, следующего за вводом в
эксплуатацию, и прекращается в месяце выбытия. Амортизируемая база —
первоначальная стоимость за вычетом ликвидационной (IAS 16 §53); ниже
ликвидационной стоимость не опускается. В последнем месяце срока
доначисляется весь остаток базы, чтобы на счёте 02 не оставался «хвост»
от округлений.

**Проводки** формируются автоматически:

| Операция | Дт | Кт |
|---|---|---|
| Начисление амортизации | счёт затрат объекта (26 / 20 / 44) | 02 |
| Списание накопленной амортизации при выбытии | 02 | 01 |
| Списание остаточной стоимости | 91 | 01 |

Счёт затрат задаётся у каждого объекта: 26 — управленческие расходы,
20 — основное производство, 44 — расходы на продажу.

**Начисление за период** вызывается кнопкой «Начислить амортизацию»: система
показывает предварительный расчёт по всем объектам с суммами и причинами
пропуска (введён позже, самортизирован, уже начислено), и проводит его одним
действием. Повторное начисление за тот же месяц невозможно — ключ
«объект + период» уникален.

**Выбытие** — списание, продажа или перевод на консервацию. Консервация
оставляет объект на балансе и лишь приостанавливает начисление.

Расчёт продублирован на сервере (`apps/accounting/services.py`) и в браузере
(`static/js/core/depreciation.js`): демо-режим работает без бэкенда, поэтому
формулы обязаны существовать в обоих контурах. При правке одной стороны
правится и вторая.

## Отчётность

Отчёты строятся на **проведённых проводках** — тех же данных, что видит
пользователь в разделе «Проводки», поэтому цифры отчёта всегда совпадают с учётом.
Демо-данные тоже формируются от документов: реализация, поступление товара,
касса, банк, зарплата и налоги разносятся по двойной записи, поэтому актив
баланса равен пассиву, а обороты по дебету — оборотам по кредиту.

| Отчёт | Экран | API |
|---|---|---|
| Оборотно-сальдовая ведомость | `#/report-turnover` | `/api/reports/turnover/` |
| Бухгалтерский баланс | `#/report-balance` | `/api/reports/balance/` |
| Отчёт о прибылях и убытках | `#/report-pnl` | `/api/reports/pnl/` |
| Движение денежных средств | `#/report-cashflow` | `/api/reports/cashflow/` |
| Задолженность клиентов и поставщиков | `#/debts` | `/api/reports/debts/` |
| Журнал операций | `#/journal` | коллекция `entries` |
| Доходы и расходы | `#/analytics` | `/api/summary/` |

Центр отчётности — `#/reports`: KPI по периоду и переход в любой отчёт.
Период задаётся в самом отчёте (день, месяц, квартал, год, всё время),
любой отчёт выгружается в CSV и выводится на печать.

Контроль корректности встроен в сами отчёты: ОСВ показывает, сходятся ли
обороты, баланс — равен ли актив пассиву. Расхождение выводится баннером
со ссылкой на раздел «Проверка ошибок».

## Обмен с Excel

Единственная внешняя библиотека проекта — **SheetJS 0.18.5** (Apache-2.0, 437 КБ),
лежит локально в `app/static/vendor/sheetjs/`. Она грузится **лениво**: файл
запрашивается только когда пользователь нажал «Excel» или выбрал файл для
загрузки. На старт приложения библиотека не влияет.

**Выгрузка.** Кнопка «Excel» есть в каждой таблице системы рядом с «CSV».
В отличие от CSV, числа выгружаются числами, даты — датами, колонки получают
ширину по содержимому, а шапка закрепляется: длинный регистр листается без
потери заголовков. Бухгалтер считает выгрузку формулами сразу, не переразбирая
текст.

В центре отчётности кнопка «Выгрузить всё в Excel» собирает **одну книгу из
шести листов**: оборотно-сальдовая ведомость, баланс, отчёт о прибылях и
убытках, движение денежных средств, дебиторская и кредиторская задолженность.

**Загрузка.** «Банк → Загрузить выписку» разбирает файл Excel или CSV прямо в
браузере. Колонки ищутся по ключевым словам в заголовках, а не по фиксированному
порядку, поэтому подходят выписки разных банков:

| Поле | Распознаются заголовки |
|---|---|
| Дата | дата, date |
| Сумма | сумма, amount |
| Приход | приход, кредит, поступление, credit |
| Расход | расход, дебет, списание, debit |
| Контрагент | контрагент, плательщик, получатель, наименование, корреспондент |
| Назначение | назначение, основание, комментарий, purpose |
| Номер | номер, док, number |

Даты принимаются и как `05.08.2026`, и как `2026-08-05`; суммы — и как
`1 250 000,50`, и как `1250000.5`. Контрагенты сопоставляются со справочником.
Перед записью в учёт показывается предпросмотр: сколько операций найдено, какие
суммы, у кого контрагент не определён. Платежи создаются только после
подтверждения.

CSV-экспорт оставлен для обмена с внешними системами.

## Поиск и уведомления

**Расширенный поиск** (`#/search`) ищет одновременно по документам, договорам,
реализациям, заказам поставщикам, платежам, кассовым ордерам и проводкам.
Условия: номер или содержание, тип документа, вид документа ЭДО, контрагент,
организация, диапазон дат и диапазон сумм. Ищутся только те журналы, к которым
у роли есть доступ. Глобальная строка поиска в шапке дополнительно понимает
суммы (`150000`) и даты (`2026-08`), а последним пунктом выдачи предлагает
перейти в расширенный поиск.

**Уведомления** формируются по правилам из данных, а не задаются вручную:

| Правило | Когда срабатывает |
|---|---|
| Неоплаченные счета | долг по реализации просрочен или срок истекает в ближайшие 3 дня |
| Сроки уплаты налогов | до срока уплаты 7 дней или платёж уже просрочен |
| Отсутствие документов | у документа не загружен скан |
| Ошибки в операциях | автопроверка нашла ошибку уровня «критично» |

Правила отрабатывают при входе в систему и по кнопке «Проверить сейчас» на
экране «Уведомления»; повторные записи в ленту не попадают.

## Docker

`.env` обязателен: из него контейнеры берут `SECRET_KEY` и параметры Postgres.

```bash
cp .env.example .env      # заполнить SECRET_KEY и POSTGRES_PASSWORD
cd docker

docker compose up -d --build          # разработка → http://127.0.0.1:8080
docker compose logs -f web            # логи приложения
docker compose down                   # остановить (данные в томе сохраняются)

docker compose -f docker-compose.prod.yml up -d --build   # прод: gunicorn + nginx
```

Поднимаются два контейнера: `erp_db` (PostgreSQL 16) и `erp_web` (Django).
`scripts/entrypoint.sh` ждёт базу, применяет миграции, собирает статику и —
при `SEED_DEMO=True` — загружает демо-данные. Готовность проверяется
эндпоинтом `/api/health/` (healthcheck контейнера).

Проект назван `erp` (директива `name:` в compose-файлах), поэтому его тома
и сети получают префикс `erp_` и не пересекаются с другими проектами,
собранными из папки с тем же именем.

Полный сброс данных вместе с базой:

```bash
docker compose down -v     # удаляет том erp_postgres_data
docker compose up -d       # поднимет заново и загрузит демо-данные
```

## Настройка

Все параметры читаются из `.env` (см. `.env.example`): секретный ключ,
подключение к БД, реквизиты организации, ставки налогов, язык, часовой пояс,
параметры CORS. Без `.env` проект запускается на SQLite с настройками разработки.

| Запуск | Адрес | База данных |
|---|---|---|
| `python manage.py runserver` | http://127.0.0.1:8000/ | SQLite (`app/db.sqlite3`) |
| `docker compose up -d` | http://127.0.0.1:8080/ | PostgreSQL в контейнере `erp_db` |

Это независимые окружения: данные, внесённые в одном, во втором не появятся.
